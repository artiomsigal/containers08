# Лабораторная работа №8
## Настройка непрерывной интеграции с помощью GitHub Actions
### Цель работы
Ознакомиться с принципами непрерывной интеграции (CI) и научиться настраивать автоматический запуск тестов с помощью GitHub Actions для PHP-приложения, запущенного в контейнере Docker.
### Задание
Создать Web-приложение на PHP, реализовать работу с базой данных SQLite, написать тесты для приложения и настроить автоматический запуск тестов с использованием GitHub Actions.
## Описание выполнения работы
1. Создание структуры проекта
Была создана директория `containers08` со следующей структурой:
- `site/` — исходный код PHP-приложения
- `sql/ `— SQL-скрипт для создания базы данных
- `tests/` — тесты приложения
- `.github/workflows/` — конфигурация CI
- `Dockerfile` — описание контейнера
2. Разработка Web-приложения
Было создано PHP-приложение, включающее:
- класс `Database` для работы с SQLite
- класс `Page` для отображения страниц
- шаблон страницы `index.tpl`
- файл `index.php` для обработки запросов
Приложение получает данные из базы и отображает страницу.
3. Создание базы данных
В директории `sql` создан файл `schema.sql`, который:
- создаёт таблицу `page`
- добавляет тестовые данные
База данных автоматически создаётся при сборке Docker-образа.
4. Написание тестов
Создан простой тестовый фреймворк (`testframework.php`) и файл `tests.php`.
Тесты проверяют:
- подключение к базе данных
- количество записей
- создание записи
- получение записи
5. Создание Dockerfile
В Dockerfile:
- установлен SQLite
- создана база данных
- скопирован сайт в контейнер
6. Настройка GitHub Actions
Создан файл `.github/workflows/main.yml`, который:
- собирает Docker-образ
- создаёт контейнер
- копирует тесты
- запускает контейнер
- выполняет тесты
- удаляет контейнер
7. Проверка работы
После отправки проекта на GitHub тесты автоматически запускаются во вкладке **Actions**.
Все тесты успешно проходят.
## Ответы на вопросы
1. Что такое непрерывная интеграция?
Непрерывная интеграция (CI) — это практика разработки, при которой изменения кода автоматически проверяются с помощью сборки и тестов при каждом обновлении репозитория.
2. Для чего нужны юнит-тесты? Как часто их нужно запускать?
Юнит-тесты проверяют корректность работы отдельных частей программы (функций, методов).
Они позволяют быстро находить ошибки.
Запускать их нужно:
- при каждом изменении кода
- автоматически (через CI)
3. Что нужно изменить, чтобы тесты запускались при Pull Request?
Нужно изменить блок on в `.github/workflows/main.yml`:
on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main
4. Как удалять созданные образы после тестов?
Нужно добавить шаг в workflow:
 -name: Remove image
  run: docker rmi containers08
